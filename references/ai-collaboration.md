# AI 协作规范

这部分定义了 AI 在执行 PRD 管理工作时应该如何与用户交互——什么时候确认、什么时候追问、什么时候拒绝。

## 协作与范围

用户已确认的需求、设计和已有授权持续有效，不因进入下一份文档重复询问。先读取项目和对话中已有信息；只有缺失的业务规则、重大取舍或范围变化会影响正确性时，才提出具体问题。常规实现选择可自主完成并记录理由。

人负责目标、取舍与验收，AI 负责实现细节及证据。交付时围绕功能/架构、逻辑/效率、测试/边界三项报告；需要用户决定时提供具体偏差、影响和选项，无需用户逐行读代码。

- 仅请求 PRD、任务拆解或审查时交付对应产物，不自动修改产品代码。
- 已授权实现/修复时，在范围内完成实现、三轮检查和文档同步；详见 `references/implementation-review.md`。
- 小变更只更新受影响文档；用户明确排除文档或测试时尊重范围并标明验证缺口，不能虚构完成证据。项目已有强制检查按其规则处理。
- 资金精度、权限边界等业务规则不明确时先澄清具体缺口；规则和授权已明确时继续执行。
- 只使用项目真实存在的检查命令，不默认 `pnpm test:all`。按风险选取必要检查，不强制每项修改同时新增单元和集成测试。
- 测试通过、AI 审查完成、用户验收和上线是不同状态，不能互相替代。

## 质量处理

| 情况 | 行动 |
|------|------|
| 实现偏离已确认需求/契约 | 记录偏差及代码证据，在修复授权内纠正；范围变化先澄清 |
| 发现性能疑点 | 先解释规模、复杂度或调用成本，实测后再声称提速 |
| 测试失败 | 保存失败证据、定位、最小修复、原场景及关联回归；不放宽断言凑全绿 |
| 缺少运行环境 | 完成可做的静态审查，明确未测范围和所需条件 |
| 只改文案或格式 | 做针对性检查，不生成完整审查套件 |
| 用户只要报告 | 给出可复核发现和建议，不擅自修复 |

## 自检清单

### prd.md 生成后自检
- [ ] 每个需求保留了原始需求原文（未改写）？
- [ ] 每个需求有需求分析（是什么/边界/关键假设）、需求目标、使用链路？
- [ ] 使用链路超 3 步或有分支时配了流程图？有状态对象画了状态流转图？
- [ ] 定义了验收标准，且全是业务语言（使用人可照做验证）？
- [ ] 有版本级功能清单（含优先级）？
- [ ] 避免了技术实现细节？
- [ ] 包含成功指标？

### dev.md 生成后自检
- [ ] 包含数据库 Schema 变更？
- [ ] 列出了 API 接口影响清单（后端项目）？
- [ ] 考虑了向后兼容性？
- [ ] 避免了业务需求描述？
- [ ] 基于实际代码（非模板假设）？

### database.md 生成后自检（后端数据库变更时）
- [ ] 表清单总览含变更类型和关联表？
- [ ] 每张表有用途说明和字段含义表？
- [ ] 枚举值写全且带业务含义？
- [ ] 多表时含表关系图（mermaid）？
- [ ] 与实际 schema 和项目迁移一致？

### test.md 生成后自检
- [ ] 测试范围与 prd.md 功能清单一一对应？
- [ ] 按项目类型分化：后端以单元测试清单为主 / 前端含界面测试（显示/交互/适配）？
- [ ] 含使用人验收用例（前置条件+操作步骤+预期结果，业务语言）？
- [ ] 含验收记录、边界矩阵和执行证据，AI 自测与用户验收是否分开？
- [ ] 包含部署前检查清单？

### ops.md 生成后自检
- [ ] 列出了所有环境变量？
- [ ] 包含完整部署流程和回滚方案？
- [ ] 包含故障排查手册？

## 异常与变更处理

- 版本目录已存在：先读内容，按当前任务合并更新；需要替换用户内容且授权不明确时才澄清，不默认覆盖。
- 信息不完整：先读可获得的上下文并推进独立部分，只追问影响正确性的缺口，不要求用户替 AI 定位根因。
- 模板或工具不可用：说明具体限制，完成仍可进行的文档工作，未运行检查记未验证。
- 中途变更需求：更新受影响的 PRD、design.md（图/层级/交互）、dev/test/tasks 和版本记录，不整套重写。
- 已归档版本：读取作为基线，新需求或修复在当前版本记录，不改历史来隐藏缺陷。

### ASCII 设计完成后自检

- 页面/区域/控件 ID 与需求、图、层级树和表格对应？
- 层级树表达包含、复用、重复和条件显示，而非仅导航或文件目录？
- 关键组件的职责、输入、状态归属和事件处理方明确？
- 布局选择有业务理由，继承了项目视觉语言？
- 状态恢复、响应式、键盘与长内容处理已按风险说明？
- 线框排版检查与设计检查分开记录，未声称产品运行通过？
