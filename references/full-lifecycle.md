# 从需求到交付

按用户请求选择阶段。完整流程可为 `PRD → ASCII 设计/技术方案 → 计划与测试 → 实现/审查 → 验收`，不是每次都生成全部文件。

## 1. 需求基线

读取项目规则和现有文档，使用 `assets/prd_template.md`。保留原话、明确范围与非目标、稳定需求 ID、功能清单、使用链路、适用状态/异常及业务验收标准。缺失信息标注假设；影响后续正确性的歧义才澄清，已有确认不重复索取。

只有 PRD 请求时在完成需求文档和必要索引后交付。

## 2. 设计与技术方案

- 有 UI：按 `references/design-guidance.md` 与 `references/ascii_design_patterns.md` 生成该版本 `design.md`，包含多页面 ASCII 线框、组件层级树、职责/状态归属、流转及设计说明。先读项目现有 UI，继承产品设计语言。仅设计请求不修改应用代码。
- 纯后端：不生成空设计稿；使用 dev.md 说明接口及数据影响。
- 技术方案：先读取目录、配置/依赖版本、实际入口、关联模块和数据模型，再写 `assets/dev_template.md`。说明当前实现与本次改动、算法/契约/不变量、文件影响、验证入口，关联需求和 ASCII 页面 ID。
- 数据模型变化：生成/更新 database.md，引用实际 schema 与迁移；优先沿用项目既有 migrations/ORM，不硬编码 MySQL、Prisma 或目录。

## 3. 配套文档

按范围补 plan/tasks、test、ops 和 CHANGELOG：计划只管责任和依赖，测试关联需求/页面/风险，运维只记录本次相关的可执行流程。纯前端静态项目不补无关数据库章节。

索引只链接实际存在的文件，设计入口为 design.md；既有按类型分目录项目用正确的相对链接。

## 4. 实现与审查

用户授权实现后按任务执行，遵循 `references/task-execution.md` 与 `references/implementation-review.md`。产品 UI 对照 ASCII 线框、组件层级与状态；在 dev.md 将语义组件映射为实际组件/文件，说明合理的实现差异。

解释实际实现 → 检查逻辑/效率 → 边界验证/修复/回归。小修改简记，复杂版本用 review.md。设计完成、构建成功、自测通过、使用人验收各自记录。

## 5. 验收与版本状态

使用人按 test.md 业务用例验收，记录实际验收人、时间和结果；尚未验收写待验收。不通过项保留证据，未发布版本原版本修复，已发布/归档或新增范围再安排新版本。

需求功能清单、任务和 README 根据证据更新状态，不能因为文件齐全就写版本已完成。
