# PRD ↔ 代码双向验证

先明确本次版本、变更范围和需求/设计基线，再读取真实代码。文档清单和搜索结果用于定位，不能单凭文件存在或测试名称判定需求实现。

## 正向：PRD → 实现 → 证据

从 PRD 功能清单提取稳定需求 ID，沿入口、核心逻辑、接口和数据读写检查行为。记录：

| 需求 ID | 设计约束 | 代码路径/符号 | 测试 ID/执行证据 | 结论/缺口 |
|---------|----------|---------------|-----------------|-----------|
| | | | | 已验证/部分实现/缺失/未验证 |

未提供代码时只能报告文档一致性；只有实现没有运行证据时，明确行为未验证。

## 反向：实际变更 → 依据

扫描本次新增或改动的入口、API、状态及数据副作用，追溯到需求或设计约束。区分新增产品能力、既有行为、必要的基础设施和重构；后两者可关联设计依据，无需为每个辅助函数虚构 PRD。

发现额外功能或行为偏差时记录，不修改 PRD 为错误实现背书。

## 审计交付

按 `references/implementation-review.md` 第一轮输出实际实现摘要和映射；用户要求完整质量审查或已经授权实现交付时，继续逻辑/效率审查和边界验证。审计请求本身不授权代码修复。

跨模块或正式审计用 `assets/review_template.md`；小范围审计可在任务记录或回复中给出结论、位置和未验证项。自动化脚本可复用项目已有检查，但静态扫描只是证据的一部分。只有发现重复的稳定检查需求时才新增脚本或 CI 配置，不默认生成不存在的审计命令。
