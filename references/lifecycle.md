# 版本生命周期：状态、基线、ID 与变更记录

## 状态机（唯一枚举）

所有文档头部的 `状态` 只能取下列值，不自造同义词（规划中、草案等统一为「草案」）。

| 状态 | 含义 | 进入条件 | 允许的改动 |
|------|------|----------|-----------|
| 草案 | 正在起草 | 创建版本 | 自由修改 |
| 待评审 | 等使用人确认 | 提交评审 | 按评审意见改 |
| 已确认 | **基线**：需求范围已定 | 使用人明确确认 | 改需求必须写修订记录，ID 不重编号 |
| 开发中 | 实现进行中 | 开始写代码 | 同上；缺陷默认原版本修复 |
| 已验收 | 使用人验收通过 | 验收记录写入 test.md/CHANGELOG | 同上 |
| 已发布 | **冻结**：已上线 | CHANGELOG 出现带日期的该版本条目 | 只允许勘误（记入 CHANGELOG 的 Fixed/勘误）；新范围、行为变更开新版本 |
| 已取代 / 已取消 / 已归档 | 旁支终态 | 明确指令 | 不改正文，只补指向说明 |

- 推进顺序：草案 → 待评审 → 已确认 → 开发中 → 已验收 → 已发布。可回退，回退要在修订记录写原因。
- 「已发布」以 `docs/prd/CHANGELOG.md` 中带日期的版本条目为准，不凭口头判断。无法确认是否已发布时先问使用人。
- 判断「原版本修还是开新版本」只看状态：未到「已发布」→ 原版本修；「已发布」及之后 → 新版本。
- README 索引的状态必须与 prd.md 头部一致；其他文档（design/dev/plan）的状态只能不超前于 prd.md。

## 文档头部（front matter）

prd.md 等主文档顶部用 YAML：

```yaml
---
version: v0.2.0
status: 已确认
based_on: v0.1.0        # 无前序版本则省略
skill_version: 0.2.0    # 生成时的 prd-manager 版本
updated: YYYY-MM-DD
---
```

## 需求 ID 生命周期

- 前缀登记（脚本据此检查冲突）：`S` 需求、`F` 功能点、`Q` 待决问题、`D` 页面（design）、`T` 任务（task）、`V` 技术验证、`I` 事故、`TC` 测试用例；优先级用 `P0/P1/P2/P3` 并只作优先级（含义见 `references/priority_definitions.md`）。页面 ID 用 `D01-orders` 形式，不用 `P01`。项目已有约定则沿用并登记在 README。
- 只增不复用：新增取新号；变更沿用旧号；**移除**的 ID 保留在需求表并标「已移除」，不删、不复用。
- 拆分：原 ID 标「已拆分 → S5a、S5b」，新 ID 写 `拆自 S5`。合并：被并 ID 标「已合并 → S3」。
- 新版本 prd.md 只写**增量**：需求表列出 `变更类型`（新增/变更/沿用/移除），沿用项只列一行并链接到上一版，不全量重述。
- 待决问题表列：`ID | 问题 | 状态(开放/已决/搁置) | 决定 | 日期 | 影响需求`。已决问题保留，不删行。

## 修订记录

基线（已确认）之后每次改需求，在 prd.md 末尾「修订记录」追加一行：`日期 | 变更 | 影响 ID | 原因 | 确认人`。同时更新受影响的 design/dev/plan（见 `references/incremental-iteration.md` 的影响表）。

## CHANGELOG

单文件 `docs/prd/CHANGELOG.md`，按 Keep a Changelog：`Unreleased` 置顶，版本倒序，发布时把 Unreleased 内容落到带日期的版本条目。撤回的版本标 `[YANKED]` 并写原因。

## 冻结清单（无 git 时的基线手段）

版本进入「已发布」时可在版本目录生成 `.freeze.json`（文件 → sha256），由 `scripts/check_docs.py --freeze <version>` 写入；之后检查脚本发现冻结文件被改会报 ERROR。有 git 的项目优先用 tag，二者可并存。
