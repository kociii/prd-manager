# 测试与验收闭环

test.md 回答「如何验证这个版本做对了」，服务两类人：开发者（开发自测）和使用人（验收）。测试不是事后补的——它在 dev.md 生成后就和代码同步演进。

## test.md 生成

使用 `assets/test_template.md` 生成 `test.md`，包含：

1. **测试范围**：与 prd.md 功能清单一一对应，每个功能点都有验证手段
2. **开发自测**（按项目类型分化）：
   - 后端：以**单元测试清单**为主——模块 / 测试场景（正常/边界/异常）/ 输入 / 预期结果。描述要测什么，不堆测试代码
   - 前端：必含**界面测试**——逐页面的显示、交互、适配、兼容验证点
   - 全栈：两者都含
3. **验收用例**：使用人验收专用，每条 = 前置条件 + 操作步骤 + 预期结果，全部业务语言
4. **部署前检查清单**：上线前必须通过的检查项
5. **验收记录**：每轮验收的结论 + 不通过项明细

## 部署前检查清单

每个版本 `test.md` 包含：
- [ ] 所有开发自测通过（单元测试 / 界面测试）
- [ ] 静态扫描无 critical 错误
- [ ] 代码审查完成
- [ ] 环境变量已配置（对照 `ops.md`）
- [ ] 数据库脚本已在测试环境验证（对照实际迁移与 `database.md`，如有）
- [ ] 回滚方案已准备

## 验收闭环（评审②）

1. 开发完成后，使用人按 test.md 第 3 章验收用例逐条验证，标记通过/不通过
2. 填写验收记录（日期、验收人、结论）
3. **不通过项**：记录实际现象、期望结果、严重度。未发布版本默认在当前版本修复并复测；已发布/归档版本或新增范围按 `references/incremental-iteration.md` 安排新版本，保留每轮失败和复测记录
4. 全部通过后回填 prd.md 功能清单的验收结果列

## 测试与代码同步

| 代码变更类型 | 同步的测试 |
|-------------|-----------|
| 新增功能 | 新增单元测试（后端）/ 界面验证点（前端）+ 更新 test.md |
| Bug 修复 | 新增回归测试（覆盖原 bug 场景）+ 更新 test.md |
| 重构 | 确保现有测试通过 + 更新测试文档 |
| API 变更 | 更新接口测试 + 更新 test.md |
| 数据库变更 | 新增迁移测试 + 更新 test.md 和 database.md |

> **为什么要回归测试？** 一个 bug 出现一次意味着这个场景之前没有测试保护。不加回归测试，3 个月后别人重构这段代码时，同样的 bug 可能再次上线。


## 按风险设计边界验证

预期来自需求、契约和业务不变量；不能按当前实现抄出必过断言。覆盖率沿用项目约定，记录统计范围，不能证明所有边界安全。纯文案/格式等低影响变更采用针对性检查，不为凑覆盖率制造测试。

| 维度 | 适用场景示例 |
|------|--------------|
| 输入与数值 | 空/缺失/非法值、最小最大值、阈值两侧、金额精度、日期/时区边界 |
| 状态与权限 | 非法状态迁移、重复操作、越权、不同用户的数据隔离 |
| 并发与幂等 | 重复回调、乱序、竞态、超时重试、部分成功及回滚 |
| 外部依赖 | 断网、超时、限流、返回错误或畸形数据 |
| 规模与资源 | 空列表、分页末页、大数据量、请求次数、资源释放 |
| 界面与兼容性 | 加载/失败/空状态、重复点击、刷新/返回、适用设备和旧契约 |

只选本次适用维度并说明未覆盖原因。资金、权限、并发和数据写入等高影响路径优先；跨组件风险用集成或界面验证，不能只测被 mock 的内部函数。

在 test.md 记录需求 ID、不变量、用例 ID、输入、预期依据、方法和执行状态。修复时先保存反例或失败证据，再做最小修复、原场景复测及受影响回归，遵循 `references/implementation-review.md` 的闭环与停止条件。

使用真实项目命令，记录环境、代码基线、结果和日志；未执行/失败/阻塞/待人工验收分别标记。不把 AI 自测写成用户验收，不从全绿用例推导“无 bug”。


界面验证关联 design.md 中的稳定页面/组件 ID、视口、状态和交互规则。检查父子事件、重复列表实例、状态归属和条件区块的实际行为，不能把线框/层级树完成等同于产品实现通过。
